## Task 4: Logic and Search

Where each idea is used in the planner:

- **Logical reasoning** decides *whether* a single action can be used in the
  current state. This is exactly `is_applicable(state, action)` in
  `planner.py`, which checks `S ⊨ Preconditions(a)`
  (`pos_preconditions ⊆ state` and `neg_preconditions ∩ state = ∅`). It is a
  purely local, one-step check — it knows nothing about the goal or about
  other actions.
- **Search** (breadth-first search over the `visited`/`queue` structure)
  decides *which sequence* of individually-applicable actions to try, in
  what order, so that a path to the goal is found (and found with the
  fewest actions, since BFS explores shorter plans first). Search is what
  turns "here are some legal single steps" into "here is a whole plan."

### Completed diagram

```
Current state
      |
Check action preconditions          <- LOGIC: is_applicable(state, action)?
      |
   [is S |= Preconditions(a) true?]  <- the "?" in the handout's diagram
      |
Generate successor state            <- LOGIC: Apply(S, a)
      |
Search over alternatives            <- SEARCH: BFS tries every applicable
      |                                 action from every frontier state
    Goal?                           <- LOGIC: goal ⊆ state (termination test)
```

In words: at each state, logic filters the full action list down to the ones
that are actually applicable (`S ⊨ Preconditions(a)`) and computes what the
world looks like after any one of them (`Apply`). Search is the outer loop
that decides which of those applicable actions to try next, and in what
order, across the whole space of states — it is what lets the agent look
several steps ahead instead of only ever checking one action at a time.
Logic determines what is possible; search determines what to try. The two
combine because search would be directionless without logic telling it
which moves are legal, and logic alone would only ever tell you about the
very next step, never a full plan.

## Task 5 (Optional): Can the LLM Verify Its Own Plan?

I asked the LLM (in the same conversation used to generate `planner.py`) to
explain why the plan `PickUp(Package,A), Move(A,B), Move(B,C), Drop(Package,C)`
is valid, by identifying each action's preconditions and showing they hold in
the state in which the action executes. The LLM's prose explanation matched
the actual states produced by `test_planner.py` in this case — but that
agreement is not what should be trusted.

**Question: which should you trust more — (a) the LLM's explanation, or (b)
the independently executed state transitions?**

**(b), the independently executed state transitions.** The LLM's explanation
is just more natural-language text generated by the same process that wrote
the code — it is not derived by actually executing the program, so an LLM
could produce a fluent, confident-sounding justification for an invalid plan
(e.g. silently assuming a precondition holds that does not, or miscounting
which location the robot is at) and the explanation would look identical in
quality to a correct one. The Python state trace in `test_planner.py`, by
contrast, is produced by mechanically applying the actual `is_applicable`/
`apply` functions to the actual state sets — if a precondition were violated,
the independent verification step (`is_applicable(s, a)` re-checked for every
action in the plan) would report `INVALID` regardless of how convincing the
LLM's prose was. This is the core point of the exercise, stated directly in
the handout: **a generated explanation is not the same as an independent
verification.**

## Task 6: Prolog as a Plan Verifier (optional)

`planner.pl` contents (facts + rule):

```prolog
connected(a,b).
connected(b,a).
connected(b,c).
connected(c,b).

can_move(X,Y) :-
    connected(X,Y).
```

Recorded results (`swipl -f planner.pl`, real run):

```
?- can_move(a,b).
true

?- can_move(a,c).
false
```

**(a) Why does Prolog return `true` for `can_move(a,b)`?**
Because `connected(a,b)` is a fact in the knowledge base, and the rule
`can_move(X,Y) :- connected(X,Y)` says `can_move(X,Y)` holds whenever
`connected(X,Y)` does. Unifying X=a, Y=b, Prolog finds `connected(a,b)`
already stated as a fact, so the rule body succeeds and so does the query.

**(b) Why does it not establish `can_move(a,c)`?**
There is no fact `connected(a,c)` in the knowledge base (A and C are not
directly connected in the warehouse — the robot must go through B), and
Prolog uses the closed-world assumption: if it cannot *derive* a goal from
the given facts and rules, it treats the goal as false. Since no chain of
facts/rules proves `connected(a,c)`, `can_move(a,c)` fails.

**(c) Relationship between the Prolog rule and Connected(X,Y) → CanMove(X,Y)?**
They are the same statement in two notations. The Prolog clause
`can_move(X,Y) :- connected(X,Y).` is Horn-clause syntax for the logical
implication `Connected(X,Y) → CanMove(X,Y)`, universally quantified over
X and Y. Querying `can_move(a,b)` is asking Prolog to check whether
`CanMove(a,b)` is entailed by the knowledge base under this implication —
exactly the `S ⊨ Preconditions(a)` style check used in `planner.py`, just
expressed as executable inference instead of a Python set-membership test.

```
?- valid_move(b,c).   true
?- valid_move(a,c).   false
```

This matches the handout's expectation exactly: the first two queries
succeed and the third fails.

**Challenge — is `Move(a,c)` supported by the warehouse knowledge?**
`?- valid_move(a,c).` returns `false` (recorded above), so no: the proposed
action `Move(a,c)` is **not** supported by the warehouse knowledge base,
because A and C are not directly `connected/2`. If the Python planner ever
proposed `Move(a,c)` directly, this independent Prolog check would catch it
even though the Python side never generates it (the warehouse actions list
in `planner.py` deliberately never includes a direct A-C move, matching the
handout's connectivity). This demonstrates the intended
Generate -> Independent verification architecture: the Python program
proposes/generates a plan, and Prolog, driven by a separately-stated logical
description of the warehouse, checks it without trusting the generator.

## Task 8: Connect Prolog to Logical Reasoning (optional)

```prolog
wet_road.

slippery :-
    wet_road.

reduce_speed :-
    slippery.
```

Recorded result (real run): `?- reduce_speed.` -> `true`.

**Why does the query succeed?** `wet_road` is asserted as a fact. The rule
`slippery :- wet_road` lets Prolog derive `slippery` from that fact. The rule
`reduce_speed :- slippery` then lets it derive `reduce_speed` from
`slippery`. Chaining these two rules from the one base fact proves the
query.

**As a sequence of implications:**

Fact ⇒ Rule ⇒ Rule ⇒ Conclusion:

```
WetRoad ⇒ (WetRoad → Slippery) ⇒ Slippery
Slippery ⇒ (Slippery → ReduceSpeed) ⇒ ReduceSpeed
```

i.e. `WetRoad, (WetRoad → Slippery), (Slippery → ReduceSpeed) ⊢ ReduceSpeed`.

## 7.2 Reflection (Prolog section)

1. **Difference between a Prolog fact and a Prolog rule?**
   A fact (e.g. `wet_road.` or `connected(a,b).`) is an unconditional
   statement asserted to be true. A rule (e.g. `slippery :- wet_road.`) is
   conditional: its head is true *if* its body can be proven true — it
   encodes an implication (`Body → Head`), not a standalone truth.

2. **How does a Prolog query correspond to asking whether something follows
   from a knowledge base?** A query `?- Goal.` asks Prolog to search the
   facts and rules for a proof of `Goal` — i.e. it asks "does
   `KnowledgeBase ⊨ Goal`?" Prolog answers `true` if it can construct such a
   derivation (chaining facts through rule bodies via unification), and
   effectively `false` (via the closed-world assumption) if it cannot.

3. **Why might it be useful to use a Prolog program to verify a plan
   generated by a Python program?** Because it gives an *independent*
   check written from the domain knowledge (which locations are connected)
   rather than from the planner's own code — if there is a bug in the
   Python program's action definitions, a warehouse-knowledge bug encoded
   separately in Prolog will not share that bug, so the two are unlikely
   to fail in the same way at once.

4. **What advantage does an independent verifier provide when the original
   plan was generated with the help of an LLM?** An LLM can produce code or
   explanations that look correct and read fluently while still containing
   subtle logical errors (e.g. a missing precondition, or a plausible but
   invalid transition) — exactly what Task 5 warns about, that "a generated
   explanation is not the same as an independent verification." A separate
   verifier, built from first principles on the actual domain facts and not
   trusting anything the LLM asserted, catches such errors instead of
   silently propagating the LLM's own mistakes as if they were confirmed.

## Reflection Questions (Section 5)

1. **Why is it useful to specify action preconditions and effects before
   asking an LLM to write the planner?** It turns a vague request ("write a
   planning agent") into a precise, checkable specification. Without an
   explicit state/precondition/effect model to hand the LLM, there is no
   principled way to judge whether the generated code is correct — you
   would be comparing the output only against your own vague intuition.
   Specifying it first also forces *you* to understand the problem (Task 0)
   before delegating implementation, so you can actually evaluate what the
   LLM produces rather than trusting it blindly.

2. **Example of an error from a planner that fails to check preconditions?**
   If the planner applied `Drop(Package, C)` without checking
   `Holding(Package)`, it could "drop" a package the robot was never
   carrying — e.g. from the initial state `{At(Robot,C), At(Package,A)}` it
   might jump straight to `{At(Robot,C), At(Package,A), At(Package,C)}`,
   duplicating the package in two places at once. That is a physically
   impossible state, invisibly produced because the applicability check
   (logic) was skipped.

3. **Why is a plan that "looks reasonable" not necessarily a valid plan?**
   "Looks reasonable" is a judgment about surface plausibility (action
   names sound like they'd accomplish the goal), not a check that every
   precondition genuinely held in the state where each action ran. A plan
   can read fine in English — "move to B, then to C, then drop the
   package" — while silently skipping the required `PickUp` step, which
   only shows up as an error once you actually trace the state values, as
   `test_planner.py` does.

4. **What did the LLM contribute to the implementation?** The boilerplate
   and structure of the search algorithm: the `Action` representation, the
   `is_applicable`/`apply` functions implementing the precondition-check and
   effect-update rules exactly as specified in the prompt, and the BFS loop
   with a `visited` set and no-plan-found handling — i.e. it did the
   mechanical translation of a precise specification into working Python.

5. **What did you have to verify independently?** That the generated code
   actually implements the specification correctly (e.g. that
   `is_applicable` checks *both* positive and negative preconditions
   correctly, that `apply` removes negative effects before/consistently with
   adding positive ones, and that BFS genuinely explores all reachable
   states rather than terminating early); that it produces the same plan as
   the hand-constructed one for the solvable case (Test A); that it reports
   failure rather than fabricating a plan for the impossible case (Test B);
   and that it doesn't conflate "robot reaches the goal location" with
   "package reaches the goal location" (Test C). None of this can be
   trusted from the code's appearance alone — it required actually running
   it and checking the printed states.

6. **In this laboratory, where is logical reasoning being used?** In the
   precondition/effect definitions of each action (Section 2-3 of the
   handout), in the `is_applicable` check (`S ⊨ Preconditions(a)`) that
   decides whether an action can legally execute in a given state, in the
   `Apply(S,a)` state-update rule, in the goal test (`goal ⊆ state`), and —
   in the optional section — in the Prolog facts/rules/queries used as an
   independent logical verifier of the same domain.

7. **How is planning related to the search algorithms studied in the
   previous module?** Planning here *is* graph search: each state is a
   search-tree node, each applicable action is an edge to a successor
   state, and the goal test is exactly the goal test from general search.
   BFS is used here for the same reason it's used generically — it
   guarantees the shortest solution (fewest actions) when all actions have
   equal cost. The only planning-specific addition on top of "plain" search
   is that the successor function is not given directly as a graph, but is
   *derived* from the logical precondition/effect description of each
   action — which is exactly the "Logic + Search = Planning" idea stated
   at the start of the handout.

## Takeaway

Logical reasoning determines *whether* an action is applicable and *what*
the world looks like after applying it; search determines *which* sequence
of applicable actions to try in order to reach the goal. An LLM can
translate a precise specification of these two pieces into working code
quickly, but the resulting agent still has to be tested against solvable,
impossible, and misleading (irrelevant-action) cases before it can be
trusted — and any explanation the LLM gives for *why* its output is correct
is not itself a substitute for independently executing and checking that
output. This matches the general engineering pattern used throughout:
**Understand -> Specify -> Generate -> Execute -> Verify.**
